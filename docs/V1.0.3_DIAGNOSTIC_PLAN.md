# Palworld v1.0.3 Diagnostic Plan

Working plan for root-causing the confirmed, unfixed problem recorded in
`docs/linux-port-status.md` §9, problem 2: cross-registration completes
cleanly (`FULL_PLAN_REGISTER SUMMARY blocked=0 exceptions=0`, `REG_META
RESULT=PASS`) on Palworld v1.0.3, but has no visible effect. Guild-wide
materials never appear at non-main camps. This is not the
`HookEngineTick` `SIGSEGV` (that's problem 1, has a partial mitigation,
and is a different bug with different symptoms).

This can't be solved by reading further. It needs live instrumentation
against a real v1.0.3 server, the same way every other stage in this
project's history was actually resolved. Treat this as a sequence of
diagnostic stages, not a single patch. The steps below are ordered from
cheapest and highest-payoff through to most involved: check the cheap
thing first.

## Step 0: Pin the environment before touching code

- Confirm exact Palworld build (`appmanifest_2394010.acf` to `buildid`,
  same method used to confirm production was on `24575149`).
- Confirm exact NullPrism/RE-UE4SS-Linux version. Only two tags exist on
  `NullPrism/RE-UE4SS-Linux`: `linux-v0.1.0` (what we ship against, and
  what w00z001's own report confirms they were running) and
  `linux-v0.1.1`. The diff between them has been checked directly: the
  only functionally relevant change is SELinux preflight tooling and
  documentation (commit `81502b6`, see Step 1 below). Everything else is
  removal of unrelated example mods (`EventViewerMod`,
  `KismetDebuggerMod`) and Windows-only build tooling cleanup. No core
  loader source changed, so `v0.1.1` should be ABI-compatible with our
  existing `main.so`. Safe to test against, and worth upgrading to on the
  test server regardless of what this investigation finds, since it's
  likely what most future users will actually be running. Test against
  `v0.1.0` first though, since that's what's actually shipped and what
  the one confirmed report used. Don't switch the shipped baseline
  without a reason.
- Use the isolated NullPrism test server for this, updated to v1.0.3, not
  production. This is exploratory instrumentation, not a release
  candidate.

## Step 1: Rule out stale SELinux labels first, it's cheap

Check this before setting up any live reproduction.
`NullPrism/RE-UE4SS-Linux` commit `81502b6` ("detect stale SELinux
labels after game updates") describes exactly the shape of failure we're
chasing: a Steam update replaces the game executable with a new inode,
and unless a persistent `semanage fcontext` mapping was defined and
`restorecon` re-run afterwards, the replacement can silently pick up the
directory's default SELinux type instead of the custom one UE4SS's
scoped policy expects. Under the default `warn` preflight mode, that
doesn't block startup, it just risks specific operations quietly failing
while everything else carries on. That matches our symptom far better
than a hard crash would.

w00z001's environment is Fedora CoreOS with SELinux enforcing, stated
explicitly in their report. This is checkable in minutes, with no test
environment required:

- Ask them to run `ausearch -m avc -ts recent` (or check
  `journalctl -t setroubleshoot`) for denial entries around when they
  first saw the bug, and after the v1.0.3 update specifically.
- Ask them to run `ls -Z` on `PalServer-Linux-Shipping` and compare it
  against the expected type from their `semanage fcontext` mapping, if
  they have one.
- Check whether our own test and production servers even run SELinux
  enforcing at all. If they don't (Unraid typically doesn't, but confirm
  rather than assume), that alone would explain "works for us, doesn't
  for them" cleanly, without needing anything else in this plan.

If this comes back positive, the fix is a documentation/support answer
for SELinux-enforcing users (run `restorecon` after every game update),
not a code change in this mod at all, and the remaining steps below
become optional follow-up rather than required work.

## Step 2: Reproduce cleanly, unmodified

Deploy the current released `main.so` (`d82fb4d7a4...`, unmodified)
against the pinned v1.0.3 environment. Reproduce w00z001's exact report:
multi-camp guild, confirm `FULL_PLAN_REGISTER SUMMARY` / `REG_META` look
identical to their log, and confirm the build menu at a non-main camp
shows only local materials. Don't proceed to instrumentation until this
reproduces. Working from someone else's logs alone risks chasing the
wrong thing.

## Step 3: Prove or disprove that the call has any effect at all

Right now, `run_controlled_full_plan_registration` calls
`pair.storage->ProcessEvent(metadata.function, parameters.get())` and
treats "didn't throw" as success. Add an immediate read-back directly
after that call: query the destination storage module's actual container
list (`ContainerInfos` / `GuildContainerInfo`, whichever the accepted
Stage 4c/4d path already resolves) and log whether the just-registered
chest's `PalContainerId` now appears in it.

New log line, for example:
```
POST_CALL_VERIFY chest=<id> storage=<id> found_in_container_list=0/1
```

This is the single most important new data point. It directly answers
"did the call do anything," independent of whether it excepted, and
independent of what the build menu shows, which could itself be a
display issue rather than a registration issue. Don't assume which side
is broken before this confirms it.

## Step 4: Fuller signature comparison against the known-good v1.0.2 baseline

Current `REG_META` only logs `parms=8 ... flags=0x18001000000280` for the
resolved `OnAvailableConcreteModel_ServerInternal`, and that already
matches between v1.0.2 and v1.0.3 (confirmed: w00z001's log shows the
identical values). So whatever changed isn't visible in what we currently
check. Extend the dump: full property list for every parameter (name,
offset, size, not just the one currently logged), full `FunctionFlags`
bitmask, and bytecode length if reachable. Diff against the equivalent
captured during original v1.0.2 development (the project's historical
`REG_META`/reflection logs from the release-testing period are the
baseline).

Also re-verify the concrete-model and storage-module `UClass`es
themselves haven't shifted layout. A lightweight repeat of the original
Stage 4c/4d class-identity work, scoped to *confirming* prior findings
still hold, not rediscovering from scratch.

## Step 5: Look for new native-side gating, empirically

If steps 1-4 don't explain it, the function's own internal logic (not
its reflected signature) likely gained a new precondition on v1.0.3 that
silently short-circuits. This needs controlled variant testing, the same
style as the original Stage 4 A/B work:

- Does it depend on guild size (small vs. large guild)?
- Does it depend on physical distance between camps?
- Does it depend on which storage/container class variant is involved?
- Does removing/re-adding the destination camp's storage module change
  anything? (Rules out a stale-pointer/cache explanation.)

## Step 6: Fix path depends entirely on what the earlier steps find

- If it's SELinux (Step 1): document it for affected users, and consider
  a startup-time warning in our own mod if there's a cheap way to detect
  a mislabelled host process. Worth scoping separately once confirmed,
  not assumed here.
- If it's a changed struct layout or a different function now being the
  real mechanism: adapt the call site accordingly. Same kind of "find the
  real native mechanism via reflection" work this project has done from
  the start, not a guess-and-check patch.
- If it traces back to NullPrism/loader behaviour rather than Palworld's
  own engine: file upstream against `NullPrism/RE-UE4SS-Linux` with the
  concrete evidence from steps 3-5, don't just link this project's issue.

## What NOT to do

- Don't ship a "fix" that only makes problem 2 stop looking broken (for
  example, suppressing the false-clean `FULL_PLAN_REGISTER SUMMARY`)
  without actually restoring registration. That would make the bug
  harder to diagnose for the next person, not easier.
- Don't conflate this with problem 1 (`HookEngineTick` `SIGSEGV`), or
  assume `EngineTickResolveMethod = VTable` is relevant here. The
  evidence so far says it isn't, since w00z001's `EngineTick` is clearly
  firing fine.
- Don't treat a NullPrism version upgrade as a fix on its own. The
  `v0.1.0` to `v0.1.1` diff shows no core loader change, only SELinux
  tooling and docs that still need a server operator to act on manually.
  Upgrading is worth doing for other reasons (matching what most future
  users will run), but it won't silently resolve this bug by itself.
