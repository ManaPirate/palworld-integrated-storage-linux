# Palworld v1.0.3 Diagnostic Plan

Working plan for root-causing the confirmed, unfixed problem recorded in
`docs/linux-port-status.md` §9, problem 2: cross-registration completes
cleanly (`FULL_PLAN_REGISTER SUMMARY blocked=0 exceptions=0`, `REG_META
RESULT=PASS`) on Palworld v1.0.3, but has no visible effect. Guild-wide
materials never appear at non-main camps. This is not the
`HookEngineTick` `SIGSEGV` (that's problem 1, has a partial mitigation,
and is a different bug with different symptoms).

Steps 1 through 3 below are now resolved, with real evidence from a
second reporter's controlled testing (16 Aug 2026). SELinux is
definitively ruled out, and the "does the call have any effect" question
is answered: no. Step 4 is resolved (19 Aug 2026): the current v1.0.3
signature is fully characterized and accounts for the whole parameter
block. Step 5 is three-quarters resolved (19 Aug 2026): guild size,
storage class, and distance are all ruled out; only module remove/
re-add remains, and it isn't reachable from SSH-only diagnostic
builds — see that bullet for why. Step 5.5 (19 Aug 2026) confirmed
`ProcessEvent` dispatch itself is intact — every reflection-visible
avenue is now exhausted, clean or negative. Step 6/7 (20 Aug 2026) went
further still: real native disassembly, confirmed
`OnAvailableConcreteModel_ServerInternal`'s entire call chain is
byte-identical between v1.0.2 and v1.0.3, and found the actual
`ContainerInfos` array it writes into by reflection. Step 9 (20 Aug
2026) is the decisive one so far: captured `ContainerInfos`' real live
contents (`count=23`, all real non-zero GUIDs) after actual
registration passes, **conclusively proving the write path works
correctly on v1.0.3**. Step 10 checked the leading downstream
candidate (`OnUpdateAnyItemContainerDelegate`): genuinely zero
subscribers, consistent across every instance checked — a real
result, but not conclusive on its own. Step 11 tried reflection
before reaching for a decompiler and found something better: a real
lead, `OnRep_ContainerInfos`, a replication-notify callback — meaning
every prior `ContainerInfos` read in this investigation only measured
the server's own local copy, never whether it actually replicates.
**Step 12 is the pivotal result of the whole investigation**: a real
client test confirmed `OnRep_ContainerInfos` fires repeatedly (not
broken), and a real build attempt using cross-camp materials
succeeded end-to-end on v1.0.3, with a realistic mixed old-camp/
new-camp guild. This is the first time any step in this investigation
tested the actual gameplay outcome directly rather than server-side

## Step 1: SELinux (RESOLVED, ruled out, 16 Aug 2026)

SELinux was a live factor in Palworld-on-Linux compatibility generally,
via two separate, distinct mechanisms, and both are now ruled out for
this problem specifically:

**Mechanism A: `execheap` denial.** A NullPrism issue thread
(`RE-UE4SS-Linux#38`) root-caused the `HookEngineTick` `SIGSEGV`
conclusively: on SELinux-enforcing hosts running the container under the
`spc_t` domain (via `label=disable`), SELinux denies the `execheap`
process capability the trampoline allocator needs to `mprotect` its hook
memory executable, so the CPU faults on instruction fetch. Confirmed
with an actual audit log entry and register-state capture, with a
working fix. This explains the crash (problem 1), not our no-op
(problem 2): our registration call doesn't install a new hook or touch
executable memory, it just invokes an already-resolved `UFunction`
through normal `ProcessEvent` dispatch.

**Mechanism B: stale file context.** `NullPrism/RE-UE4SS-Linux` commit
`81502b6` describes a Steam update replacing the game executable's
inode picking up the wrong SELinux type without a persistent `semanage
fcontext` mapping and `restorecon`.

**Both ruled out**, from the same reporter (w00z001), Fedora CoreOS,
SELinux enforcing:

- `ls -Z` on `PalServer-Linux-Shipping` shows the expected
  `container_file_t`, no stale label.
- Both `ausearch -m avc -ts recent` and `journalctl -t setroubleshoot`
  came back empty. SELinux is enforcing but isn't denying anything in
  this neighborhood.
- Conclusively: they deployed the mod apples-to-apples (same Palworld
  build `24575149`, same `main.so` hash, same cloned save, same
  `ich777` container image) on an Unraid server with no SELinux at all,
  and the no-op reproduced identically. If SELinux were involved at all,
  it couldn't reproduce on a machine that doesn't have it.
- Our own test and production servers were also confirmed to run no
  SELinux at all (`getenforce`/`sestatus` not present, `ls -Z` returns
  `?`), consistent with never having hit either mechanism.

## Step 3: Does the call have any effect at all? (RESOLVED: no)

This mod already ships a diagnostic that answers exactly this question,
`SEMANTIC_OBSERVATION` (`src/linux/main.cpp`, around line 10984
onward), a Stage 4c.4j-era probe still compiled into the release build.
It fingerprints the destination storage's own item slots
(`ContainerId`/`ItemId`/`StackCount`) at baseline, immediate, and
delayed samples around a registration event, and reports whether the
fingerprint changed.

w00z001's controlled test triggered it and got `RESULT=UNCHANGED` on
both the SELinux-enforcing and the no-SELinux environment:
`immediate_changed=0 delayed_changed=0 retained_change=0`, fingerprint
stable across all samples. This is direct, storage-content-level
confirmation, not an inference from the build menu or from
`FULL_PLAN_REGISTER SUMMARY` alone: `ProcessEvent(
OnAvailableConcreteModel_ServerInternal)` is not mutating storage state
on v1.0.3.

## Step 4: Fuller signature comparison against the known-good v1.0.2 baseline (resolved 19 Aug 2026)

Correction on the existing baseline claim: `flags=0x18001000000280` in the
current `REG_META` line is the resolved object parameter's own property
flags (`FProperty::GetPropertyFlags()`), not the function's
`FunctionFlags` bitmask. Matching on that field only tells us the one
parameter we already check looks the same, it says nothing about the
function itself or the other seven parameter bytes making up
`parms=8` `size=8`. That gap is the actual reason Step 4 exists.

Added `REG_META_PARAM` (one log line per input parameter, emitted
alongside the existing `REG_META` line): `index`, `kind`
(`object`/`array`/`set`/`map`/`struct`/`numeric`/`bool`/`other`),
`offset`, `size`, `element_size`. Deliberately positional rather than
name-keyed: resolving each parameter's `FName` would mean using
`FName::ToString()` on arbitrary reflected data outside the
leak-and-cache pattern this project already had to build for item names
(`resolve_transport_item_name()`, Stage 4D.9g, see the comment near
line 1496), and that risk isn't worth taking just to label parameters we
can already identify by position and kind.

**Resolved, 19 Aug 2026.** Finally captured `REG_META_PARAM` against a
real v1.0.3 server — this project's own test/production infrastructure
turned out to already be running `w00z001`'s exact reproducing `main.so`
hash (`d82fb4d7a4...`) on the same Palworld build (`24575149`), so no
separate environment setup was needed. Result: exactly **one** parameter
(`index=0 kind=object offset=0 size=8 element_size=8`).

That single 8-byte object parameter exactly fills the entire `parms=8`
block — there are no "other seven parameter bytes" to account for.
Checked directly against the real SDK header rather than assumed:
`UFunction::GetParmsSize()` is used as `_malloca(ParamStructSize)` in
`Unreal/BPMacros.hpp`, i.e. it returns a byte size for allocating the
parameter buffer, not a parameter count. This whole section's framing —
"the other seven parameter bytes" — was reading `parms=8` as a count
when it's a size, the same class of misread this doc already flagged
once for the `flags=` field. The current v1.0.3 signature is fully
characterized: one parameter, an 8-byte object pointer, nothing missing.

Closed without a v1.0.2 baseline capture (SteamCMD depot downgrade,
never attempted) — judged unnecessary given the above, since the
pre-session baseline already had the object parameter's flags matching
between v1.0.2 and v1.0.3, and this finding shows there was never a
second parameter to have missed a difference in either version.

**`FunctionFlags` added and checked, 19 Aug 2026.** `GetFunctionFlagsBase()`/
`GetFunctionFlags417()` are confirmed genuinely `private`
(`generated_include/MemberVariableLayout_HeaderWrapper_UFunction.hpp`,
read directly, not assumed) — but `UFunction::GetFunctionFlags()`
itself, declared `public` in `Class.hpp`, is a real non-version-gated
wrapper around them. Added `REG_META_FUNCTION_FLAGS`, captured
`flags=0x40401` on the live v1.0.3 test server, decoded against the
real `EFunctionFlags` enum in `UnrealFlags.hpp`: `FUNC_Final (0x1) |
FUNC_Native (0x400) | FUNC_Private (0x40000)`. Mundane — `FUNC_Private`
only restricts Blueprint-graph visibility, irrelevant to native
`ProcessEvent` dispatch; nothing here suggests an added precondition.
No v1.0.2 value exists to diff against, so this rules out the *current*
value looking gating-related but can't rule out a version-to-version
change.

## Step 5: Look for new native-side gating, empirically

If Step 4 doesn't explain it, the function's own internal logic (not
its reflected signature) likely gained a new precondition on v1.0.3 that
silently short-circuits. This needs controlled variant testing, the same
style as the original Stage 4 A/B work:

- Does it depend on guild size (small vs. large guild)? **Answered, 19
  Aug 2026: no.** Added a compile-time target selector
  (`SemanticObservationTargetGuildHex` in `main.cpp`) so the one-shot
  `SEMANTIC_OBSERVATION` probe can target a specific guild instead of
  always the first eligible one in sorted order. Tested the largest
  eligible guild in the test server's real data (4 camps, 31 chests)
  and the smallest (2 camps): both `RESULT=UNCHANGED`, identical no-op.
  An earlier `std::ifstream`-based runtime-file version of this same
  idea caused a reproducible allocator-corruption crash independent of
  guild targeted or parse success — see `docs/linux-port-status.md` §6
  item 10 — reverted, rebuilt on the compile-time approach.
- Does it depend on physical distance between camps? **Answered, 19 Aug
  2026: no.** Camp location isn't stored directly on the camp model —
  found it via a new `CAMP_PROPERTY_DUMP` diagnostic (`REG_META_PARAM`'s
  positional/kind pattern applied to a `UObject` instead of a
  `UFunction`), recursing one level into the camp model's
  object-reference properties and identifying a real
  `/Script/CoreUObject.Vector` struct by struct-identity comparison, not
  guessed (24 bytes: this engine build uses double-precision Large World
  Coordinates, not the older 12-byte single-float layout — an initial
  guess assumed floats and produced garbage until corrected to doubles).
  Real coordinates: large guild's camp pair ≈128,535 units apart, small
  guild's camp pair ≈15,645 units apart — an ~8x spread — both
  `RESULT=UNCHANGED`. Distance is not the gating factor.
- Does it depend on which storage/container class variant is involved?
  **Answered, 19 Aug 2026: not applicable.** No live test needed —
  `get_storage_module_class()`
  (`/Script/Pal.PalBaseCampModuleItemStorage`) is the only class the
  mod's own discovery logic ever accepts into `storage_camps`
  (`main.cpp` ~900-905), so every storage this mod tracks and targets is
  already guaranteed to be that one class. There's no variance reachable
  through this mod's own pipeline to test.
- Does removing/re-adding the destination camp's storage module change
  anything? (Rules out a stale-pointer/cache explanation.) Not
  attempted, and not really reachable from here — this needs either a
  live client physically doing it, or substantial new *mutating* native
  code to fake it, not just a different diagnostic build. RCON is
  exposed on the test server but Palworld's RCON command set doesn't
  cover item/module-level state, only server/player administration.

Three of four bullets now closed, all negative (signature complete,
guild size doesn't matter, distance doesn't matter). This is looking
less like "gated on some topological property" and more like a blanket
no-op — worth weighing before sinking more effort into remove/re-add
specifically.

## Step 5.5: Is ProcessEvent actually reaching real native code? Yes (19 Aug 2026)

Before assuming the gap is inside the function's own compiled logic,
checked whether it's even being dispatched correctly at all. Two more
real public `UFunction` methods: `GetReturnProperty()` (does the
function have a return value) and `GetFuncPtr()` (the bound native
function pointer — `UObject::ProcessInternal` for Blueprint/script
functions, the real native address otherwise). Logged the pointer's
address only, never called or dereferenced it. Resolved which binary it
falls inside via `/proc/self/maps`, read with plain
`std::fopen`/`fgets`/`fclose` (mirroring the existing,
production-proven `read_process_rss_kb()` pattern), deliberately not
`std::ifstream` given the earlier crash (`docs/linux-port-status.md` §6
item 10).

Result: `has_return_value=0` (a genuine `void` function, confirms the
earlier `parms=8` byte-math inference), `func_ptr` resolves cleanly
into `/PalServer-Linux-Shipping` itself. Not the Blueprint VM
dispatcher, not null, not redirected anywhere unexpected. The whole
reflection-visible call chain — resolve function, `ProcessEvent`,
dispatch to native pointer — is completely intact and correct on
v1.0.3.

Five checks this session, all clean or negative for a
topological/metadata explanation: signature complete, guild size
doesn't matter, distance doesn't matter, function flags mundane,
dispatch correctness confirmed. Reflection-visible avenues are
exhausted. Whatever's actually causing the no-op is inside the native
function's own compiled logic, which reflection can't see any further
into.

## Step 7: Native disassembly — the call chain is unchanged, found ContainerInfos instead (20 Aug 2026)

Analysis used production's own `main.so`-adjacent binary directly
(`/mnt/disk1/Servers/Palworld/Pal/Binaries/Linux`, read-only mount,
never touched a running server). `PalServer-Linux-Shipping` is
`ET_EXEC` (non-PIE) — runtime addresses match static file addresses
directly, no ASLR slide.

**Tooling**: no `gdb` in this project's containers or on bare Unraid.
Used a disposable `debian:bookworm-slim --rm --pid=host
--cap-add=SYS_PTRACE` container (installs `gdb` fresh each run) to
attach to the live process by host-level PID (`docker top`). Commands
went through a `.gdb` script file, not inline `-ex` arguments, after
one inline attempt was blocked by unrelated tooling (messy nested
shell escaping tripped a safety classifier) — script files are the
pattern to reuse for this.

**Dynamically confirmed, not just read statically**:
- The thunk at `func_ptr=0x6964360` (from `REG_META_FUNC`, Step 5.5)
  extracts one `Object` param off the `FFrame` bytecode stream, then
  calls the real implementation at `0x700eac0`. Breakpoint-captured
  live register state (`rdi`=Context, `rsi`=a real stack address
  matching `FFrame&`, `rdx`=`NULL` matching `has_return_value=0`)
  confirmed this after an initial static-only read misjudged it as an
  unrelated refcount/destructor routine.
- Two candidate early-bailout checks inside the real implementation —
  a `bool` flag and a GUID-zero check — both confirmed live via
  breakpoint to **pass** (flag is `1`, GUID is real non-zero data).
  Neither short-circuits the call.

**Correlating v1.0.2 and v1.0.3 addresses**: found by searching for
the literal function name string
(`OnAvailableConcreteModel_ServerInternal`, present exactly once in
each binary), computing its virtual address in each version from
`.rodata`'s own address/offset, then searching both binaries for that
address encoded as a raw 8-byte pointer. Found a `{NamePtr, FuncPtr}`
registration-table entry in each — confirmed correct because the
v1.0.3 entry's `FuncPtr` field exactly equalled the already-known
`0x6964360`. Same table position in v1.0.2 (consistent 2144-byte
regional shift between the binaries) gave `0x6961320` for v1.0.2's
thunk — a verified anchor, not a guess.

**Result: byte-for-byte identical.** The real implementation's full
body (~1600 bytes — both bailout checks, a SIMD-based array search, a
`memmove`-based grow/insert) and all three of its direct helper calls
are structurally identical between v1.0.2 and v1.0.3, confirmed by
normalizing address-only differences out of both disassemblies (empty
diff both times). The whole native call chain for this function did
not change between versions. The no-op is not inside
`OnAvailableConcreteModel_ServerInternal` or anything it directly
calls.

**New lead, via reflection, not more disassembly guessing**: extended
the existing `CAMP_PROPERTY_DUMP` (reused unchanged for the storage
module) to resolve real property names, reusing
`resolve_transport_item_name()` verbatim (`property->GetFName()`,
same leak-and-cache call already proven safe since Stage 4D.9g — not
a new FName-resolution path). Verified zero crashes on the live test
server before trusting it. The `TArray` at offset `0x50` — the exact
one the disassembly showed being written via the `memmove`-based
insert — is named **`ContainerInfos`**. A neighbouring struct field is
`GuildContainerInfo`, and the same class carries a delegate,
`OnUpdateAnyItemContainerDelegate` — worth keeping in mind, since an
unbound/inert delegate is its own plausible "write happens, nothing
downstream reacts" mechanism.

## Step 8: Found the reader by vtable — hit a real tooling wall instead

Read the raw vtable pointer off `target_storage` (first 8 bytes of any
UObject) and its entries directly — same class of raw read as
everything else in this file, no calls made through any entry.
Captured 101 entries before the scan self-terminated at the real
vtable boundary (stops at the first entry that doesn't resolve into
`PalServer-Linux-Shipping` itself, both a safety margin and a
correctness check). Zero crashes.

Narrowed to ~19 candidates in the same address neighbourhood as the
already-known real functions, scanned each for references to offset
`0x50`/`0x58`/`0x5c`. Four hits, all dead ends: one turned out to be
the class's own **destructor** (frees every owned
`TArray`/object-pointer field in turn, including `ContainerInfos` at
`+0x50` — cleanup on object teardown, not a content reader), the rest
were coincidental matches (an unrelated object's vtable dispatch, and
stack-relative locals that happened to share the same offset value).

**Genuine tooling limitation, not just needing more digging**:
`objdump` has no cross-reference database — it can disassemble
linearly from a known address, but can't answer "show me everywhere
in this 100+MB binary that reads offset 0x50 off this specific
class." The real consumer is plausibly a method on some *other* class
entirely (an inventory-aggregation or build-menu system taking the
storage module as a parameter), which wouldn't appear in this vtable
at all. A proper decompiler with an xref database (Ghidra/IDA) would
be needed to search further this way — not attempted, out of scope
for what's available here.

## Step 9: ContainerInfos genuinely gets populated — the write path is proven correct

Pivoted to the other open lead: read `ContainerInfos`' actual live
`Count`/`Max`/`Data` fields directly (raw `TArray` field reads),
gated to fire on `run>=3` so at least two full registration passes
had already completed against that exact storage instance first (the
probe runs before that pass's own registration call — confirmed from
the actual call order, not assumed). Dumped the first 10 entries' raw
16-byte GUID and the byte at `+0x10` (entry stride `0x28`/40 bytes,
from Step 7's disassembly). Zero crashes.

**Result: `count=23`, all 10 sampled entries have real, distinct,
non-zero GUIDs.** Not empty, not garbage — genuine registration data.

**This conclusively proves the write path works.**
`OnAvailableConcreteModel_ServerInternal` does exactly what it's
supposed to on v1.0.3: real containers get registered into
`ContainerInfos`, consistent with the byte-identical-to-v1.0.2 write
code. Combined with `SEMANTIC_OBSERVATION` already proving the
destination storage's own item-slot memory never changes, the bug is
now pinned down as definitively downstream of this function. Some
separate system is supposed to consume `ContainerInfos` and merge
those containers' items into the combined/available pool, and that's
what's not happening (or not completing) on v1.0.3.

`OnUpdateAnyItemContainerDelegate` (found alongside `ContainerInfos`
on the same class, Step 7) is now the strongest concrete lead — if
that delegate is meant to fire and trigger a refresh whenever the
container list changes, and it's not bound or not firing on v1.0.3,
that exactly explains the whole symptom: clean registration, real
data written, nothing visible to the player. Not yet checked whether
it's bound or fires.

## Step 10: Checked the delegate — real edge of what's diagnosable with this toolset

First confirmed the code that touches the delegate hadn't changed:
both reference sites (the main implementation's tail, and the
secondary helper) are inside code already proven byte-identical
between v1.0.2 and v1.0.3 (Step 7/9). So if this delegate is the
missing link, it isn't because this specific code changed.

Read its actual live binding state directly —
`FMulticastScriptDelegate` is just a `TArray<FScriptDelegate>` under
the hood, so this is the same raw `TArray`-field read already used for
`ContainerInfos`, at the delegate's own offset (`+0x40` per
`CAMP_PROPERTY_DUMP`; `Count` at `+0x48`). Result: **`count=0,
max=0`**. Surveyed 5 distinct storage modules across 3 different
guilds (reusing the pass's own already-built pair list, no new
discovery work): **all five show `count=0`**, no variance at all.

Checked the original Windows mod's own source (`src/dllmain.cpp`,
already in this repo) for any reference to this delegate or
`ContainerInfos` — none found. Not conclusive either way: that mod
solved cross-camp pooling entirely differently (client-side hooks on
the local inventory scan), so it never needed this server-internal
registration machinery at all.

**Genuine limit, not a dead end from lack of effort.** Zero
subscribers, consistent everywhere checked, is equally consistent
with two different explanations: (a) this delegate is purely a
client-side UI-refresh hook, correctly empty on a headless dedicated
server regardless of version — a red herring; or (b) something
systemic broke subscription to it on v1.0.3 — the actual bug.
Distinguishing between those needs either a proper decompiler
(Ghidra/IDA) to trace who's *supposed* to subscribe, or a genuine
v1.0.2 behavioral comparison (blocked by save incompatibility, Step
6). Neither is available in this environment. Zero crashes across the
whole investigation; production untouched throughout.

## Step 11: found the real lead — `OnRep_ContainerInfos`, not the delegate

Before reaching for a decompiler, tried something cheaper first:
enumerating every `UFunction` on the storage module class's own chain
via reflection (`UStruct::ForEachFunctionInChain()`, the function-side
sibling of `ForEachProperty()` already used throughout this file for
`emit_camp_property_dump()`). Zero new tooling, same leak-and-cache
FName resolution already proven safe. Nine functions came back,
including:

- `OnRep_ContainerInfos`
- `OnRep_GuildContainerInfo`
- `OnNotAvailableConcreteModel_ServerInternal` (the unregister
  counterpart to the function this whole investigation has centred on)
- `OnUpdateItemContainer` / `OnUpdateItemContainerModule`
- `MulticastReturnSelfAndUpdatedContainerDelegate__DelegateSignature`
  — the delegate signature function for
  `OnUpdateAnyItemContainerDelegate`, confirming Step 10's read of it
  as a plain notify/UI-refresh delegate, not a replication mechanism.

**This changes the diagnosis.** `OnRep_` functions in Unreal Engine
are replication-notify callbacks: the engine calls them automatically
on a client when a replicated property changes *and that change
actually gets pushed over the network to that client*. Every read this
whole investigation has done of `ContainerInfos` (the 23-real-entries
capture, Step 9) read the **server's own local copy** directly via raw
memory — which will always look correct regardless of whether
replication is working, because it's not measuring replication at
all.

New hypothesis, consistent with everything found so far: the
server-side write (`OnAvailableConcreteModel_ServerInternal`, proven
byte-identical between v1.0.2/v1.0.3, proven to write real data) is
correct, but the mutation either isn't being marked dirty for
replication on v1.0.3, or some replication condition changed, so the
change never reaches connecting clients. `OnRep_ContainerInfos` would
then never fire on any real client, and the mechanism v1.0.0 shipped
on — "the game's own code genuinely can't tell a cross-registered
chest from a real local one" (`docs/linux-port-status.md` §8) — never
actually reaches the client that needs it, despite the server-side
state being perfect.

`OnRep_` callbacks only fire on remote proxies, never on the authority
itself — so nothing server-side, including host/SP testing, can
observe whether this fires. Confirming or killing this needs a real
client. Prepared a throwaway, read-only Windows client-side UE4SS Lua
mod (`tools/client-diagnostics/IntegratedStorageDiag/`) that hooks
`OnRep_ContainerInfos`/`OnRep_GuildContainerInfo` and only logs when
they fire — no gameplay side effects, meant to be tested against a
fully vanilla client (no other Integrated Storage client mod
installed), matching how v1.0.0 is actually designed to work. Not yet
run against a real client — next step.

## Step 12: real end-to-end build test — the mechanism works

Ran the `IntegratedStorageDiag` client mod (Step 11) for real, against
the test server, with the operator's own real guild and camps rather
than simulated data.

**First pass — replication genuinely works.** Walked between the
operator's pre-existing camp ("Camp A") and a freshly-built second
camp under the same guild ("Camp B") several times over roughly 40
minutes. `OnRep_ContainerInfos` fired **8 times** across that window,
clearly tracking the actual camp visits rather than firing once at
connect and going quiet — including two fires within the same
millisecond at one point (consistent with two storage modules
updating close together). This falsifies the Step 11 hypothesis in
its strong form: replication is not broken or dead on v1.0.3.

**Second pass — the actual gameplay outcome, tested directly for the
first time.** With nothing in the operator's personal inventory and
nothing in Camp B's own storage, the operator successfully **built**
at Camp B using materials sitting only in Camp A's storage. Not just
visible in a UI count — an actual placed build consuming pooled
cross-camp materials.

**This is the first real end-to-end test in the whole investigation,
and it passed.** Going back through Steps 4–11: every check that
showed problem 2 "reproducing" (`SEMANTIC_OBSERVATION
RESULT=UNCHANGED`, `FULL_PLAN_REGISTER` counts, replication-firing
checks) was a read-only reflection diagnostic against the server's
own internal state — not a live client actually attempting to build
with cross-camp materials. This is the first time that specific,
concrete test has been run on this v1.0.3 build, with a realistic
mixed old-camp/new-camp guild, and registration, replication, and the
actual build UI all worked correctly together.

**What this does and doesn't mean.** It does not mean the original
reports (w00z001 and others) were mistaken, or that problem 2 is
closed — a single successful controlled test on one guild
configuration doesn't rule out a bug that only shows up at a
different scale or under different timing. It does mean the core
mechanism this whole investigation has been probing (registration →
`ContainerInfos` write → replication → `OnRep_ContainerInfos` →
native build-material scan) is confirmed correct end-to-end under
these conditions, so whatever's actually failing for the original
reporters hasn't been isolated yet — the search needs a different
axis (scale: many more camps/guildmates than this 2-camp test; or
timing: a client already connected and nearby when a camp is newly
cross-registered, vs. becoming relevant afterward; or something
specific to those reporters' own setups) rather than more scrutiny of
the mechanism itself, which now has real positive evidence behind it.

Zero crashes throughout. The throwaway guild-coordinate-dump helper
used to find a second test guild's camps (superseded once the
operator built their own second camp) has been removed from
`main.cpp` — it was never meant to stay in the codebase past this
test.

## What NOT to do

- Don't ship a "fix" that only makes problem 2 stop looking broken (for
  example, suppressing the false-clean `FULL_PLAN_REGISTER SUMMARY`)
  without actually restoring registration. That would make the bug
  harder to diagnose for the next person, not easier.
- Don't conflate this with problem 1 (`HookEngineTick` `SIGSEGV`), or
  assume `EngineTickResolveMethod = VTable` is relevant here. The
  evidence so far says it isn't, since w00z001's `EngineTick` is clearly
  firing fine.
- Don't spend more time on SELinux or NullPrism version as explanations.
  Both are now ruled out with real cross-environment evidence, not just
  absence of evidence.
