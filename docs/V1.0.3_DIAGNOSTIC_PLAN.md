# Palworld v1.0.3 Diagnostic Plan

Working plan for root-causing the confirmed, unfixed problem recorded in
`docs/linux-port-status.md` §9, problem 2: cross-registration completes
cleanly (`FULL_PLAN_REGISTER SUMMARY blocked=0 exceptions=0`, `REG_META
RESULT=PASS`) on Palworld v1.0.3, but has no visible effect — guild-wide
materials never appear at non-main camps. Not the `HookEngineTick`
`SIGSEGV` (that's problem 1, has a partial mitigation, is a different bug
with different symptoms).

This cannot be solved by reading further — it needs live instrumentation
against a real v1.0.3 server, the same way every other stage in this
project's history was actually resolved. Treat this as a sequence of
diagnostic stages, not a single patch.

## Step 0: Pin the environment before touching code

- Confirm exact Palworld build (`appmanifest_2394010.acf` → `buildid`,
  same method used to confirm production was on `24575149`).
- Confirm exact NullPrism/RE-UE4SS-Linux version. **Do not assume this is
  irrelevant**: the upstream issue's own repro steps reference
  `linux-v0.1.1`, but w00z001's report and our own `BUILD-PROVENANCE.txt`
  are both `linux-v0.1.0`. Test against `v0.1.0` first (matches what's
  actually shipped and what the confirmed report used); note if `v0.1.1`
  is available and whether it changes anything, but don't switch the
  shipped baseline without a reason.
- Use the isolated NullPrism test server for this, updated to v1.0.3, not
  production — this is exploratory instrumentation, not a release
  candidate.

## Step 1: Reproduce cleanly, unmodified

Deploy the current released `main.so` (`d82fb4d7a4...`, unmodified)
against the pinned v1.0.3 environment. Reproduce w00z001's exact report:
multi-camp guild, confirm `FULL_PLAN_REGISTER SUMMARY` / `REG_META` look
identical to their log, confirm the build menu at a non-main camp shows
only local materials. Don't proceed to instrumentation until this
reproduces — working from someone else's logs alone risks chasing the
wrong thing.

## Step 2: Prove or disprove that the call has any effect at all

Right now, `run_controlled_full_plan_registration` calls
`pair.storage->ProcessEvent(metadata.function, parameters.get())` and
treats "didn't throw" as success. Add an immediate read-back directly
after that call: query the destination storage module's actual container
list (`ContainerInfos` / `GuildContainerInfo`, whichever the accepted
Stage 4c/4d path already resolves) and log whether the just-registered
chest's `PalContainerId` now appears in it.

New log line, e.g.:
```
POST_CALL_VERIFY chest=<id> storage=<id> found_in_container_list=0/1
```

This is the single most important new data point — it directly answers
"did the call do anything," independent of whether it excepted, and
independent of what the build menu shows (which could itself be a display
issue rather than a registration issue — don't assume which side is
broken before this confirms it).

## Step 3: Fuller signature comparison against the known-good v1.0.2 baseline

Current `REG_META` only logs `parms=8 ... flags=0x18001000000280` for the
resolved `OnAvailableConcreteModel_ServerInternal` — and that already
matches between v1.0.2 and v1.0.3 (confirmed: w00z001's log shows the
identical values). So whatever changed, it is not visible in what we
currently check. Extend the dump: full property list for every parameter
(name, offset, size — not just the one currently logged), full
`FunctionFlags` bitmask, and if reachable, bytecode length. Diff against
the equivalent captured during original v1.0.2 development (the
project's historical `REG_META`/reflection logs from the release-testing
period are the baseline).

Also re-verify the concrete-model and storage-module `UClass`es
themselves haven't shifted layout — a lightweight repeat of the original
Stage 4c/4d class-identity work, scoped to *confirming* prior findings
still hold, not rediscovering from scratch.

## Step 4: Look for new native-side gating, empirically

If steps 2-3 don't explain it, the function's own internal logic (not its
reflected signature) likely gained a new precondition on v1.0.3 that
silently short-circuits. This needs controlled variant testing, the same
style as the original Stage 4 A/B work:

- Does it depend on guild size (small vs. large guild)?
- Does it depend on physical distance between camps?
- Does it depend on which storage/container class variant is involved?
- Does removing/re-adding the destination camp's storage module change
  anything (rules out a stale-pointer/cache explanation)?

## Step 5: Fix path depends entirely on what steps 2-4 find

- If it's a changed struct layout or a different function now being the
  real mechanism: adapt the call site accordingly (same kind of "find the
  real native mechanism via reflection" work this project has done from
  the start — not a guess-and-check patch).
- If it traces back to NullPrism/loader behavior rather than Palworld's
  own engine: file upstream against `NullPrism/RE-UE4SS-Linux` with the
  concrete evidence from steps 2-4, don't just link this project's issue.

## What NOT to do

- Don't ship a "fix" that only makes problem 2 stop looking broken (e.g.,
  suppressing the false-clean `FULL_PLAN_REGISTER SUMMARY`) without
  actually restoring registration — that would make the bug harder to
  diagnose for the next person, not easier.
- Don't conflate this with problem 1 (`HookEngineTick` `SIGSEGV`) or
  assume `EngineTickResolveMethod = VTable` is relevant here — the
  evidence so far says it isn't (w00z001's `EngineTick` is clearly firing
  fine).
